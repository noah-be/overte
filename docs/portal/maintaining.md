# Maintaining the documentation

Portal sources and configuration live in `docs/portal` in **noah-be/overte**.
Sphinx reads the explicitly selected repository pages directly. Common guides
keep their existing paths and remain authoritative; add summaries and links
rather than copying their procedures.

## Build locally

Use Python 3.12 or newer for the pinned Sphinx version. From the repository root:

```bash
python3 -m venv build/docs-env
build/docs-env/bin/python -m pip install -r docs/portal/requirements.txt
build/docs-env/bin/python -m sphinx -b html -c docs/portal \
  -W --keep-going -n . build/docs/html
```

The HTML entry point is `build/docs/html/index.html`, which opens the portal
homepage. The search page is generated by Sphinx. To preview through a local HTTP server:

```bash
build/docs-env/bin/python -m http.server 8765 --bind 127.0.0.1 \
  --directory build/docs/html
```

Open `http://127.0.0.1:8765/`, then stop the server when
finished. Build output and the environment are ignored by Git.

The first implementation is a local, reviewable portal. Website deployment
and additional CI workflows have not been activated. An HTML build does not
trigger Jenkins or GitHub device tests.

## Add or update a page

1. Write English Markdown with one clear title and task-oriented sections.
2. Add `scope` and `last-reviewed` in its YAML header. Use a quoted
   `YYYY-MM-DD` review date. Portal builds reject absent or invalid metadata.
3. Link the page from [the portal navigation](index.md). For a canonical guide
   outside `docs/portal`, add its exact path to `include_patterns` in `conf.py`
   and its document name to the navigation.
4. Update the authoritative procedure alongside command, prerequisite or
   implementation changes, then run the build and repository documentation
   checks.

**Last updated** is generated for every page from the latest commit that changed
its source file in the checked-out revision. It uses the commit's calendar date
and follows file renames. Unrelated commits and the build date do not advance
it. No manual `last-updated` field is needed; existing fields are ignored.

The same Git history is available on GitHub after publication. The portal
reports the version it was built from; it does not query GitHub in the browser.
Rebuild after updating the checkout to show newer committed changes. Cached
builds also refresh the date panels. A future CI checkout must fetch full history
(for GitHub Actions, use `fetch-depth: 0`). Shallow checkouts or source archives
show an unavailable date rather than guessing from incomplete history.
Uncommitted files show **Not committed**; edits to a committed file add
**local changes** beside its last commit date until committed and rebuilt.

`last-reviewed` records an actual
review against named source/configuration evidence; it can be later than the
content change. A build or typo fix alone is not a technical review. Keep a
dated laboratory snapshot separate from general instructions.

Existing reference pages show **Not recorded** for review until an explicit
review date exists. The page status panel
does not use today's build date as a freshness claim. Only a page's owning
procedure can justify its review metadata.

## Verify changes

```bash
build/docs-env/bin/python -m unittest discover -s docs/portal -p 'test_*.py'
python3 tests/check-documentation.py --all
python3 tests/run-project-tests.py --profile quick --timeout 240
git diff --check
```

Prepare the [quick-profile environment](../../tests/PROJECT_TESTING.md#host-prerequisites)
first. The strict HTML build fails unresolved local document references.
Links to existing repository Markdown outside the selected portal become
explicit GitHub links to the fork's current `main`; product pages must name
their owning branch. The offline repository checker verifies local file paths
and anchors. Remote-link availability requires a separate online check.

## Preserve history and sources

Current instructions describe current behavior. Date qualification reports
and laboratory snapshots, and record the tested revision and environment.
Keep stale observations as labelled historical evidence instead of rewriting
them as a new pass. Maintain upstream provenance when reusing content; see
[Upstream documentation](upstream.md).
