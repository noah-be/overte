# Native iOS rendering integration audit

[`ios/rendering-integration-inventory.json`](../../ios/rendering-integration-inventory.json) records the source-backed path from `entities-renderer` through the existing GPU abstraction to Vulkan, MoltenVK, and a Metal-backed swapchain. It is an audit of the real renderer and does not treat bootstrap Metal geometry as evidence.

Run the drift validator on any host:

```sh
python3 ios/tests/rendering-integration-inventory-test.py
```

MoltenVK discovery, static linkage, `VK_USE_PLATFORM_METAL_EXT`, and the `vkCreateMetalSurfaceEXT` implementation are present. The static target propagates Foundation, Metal, QuartzCore, and IOSurface; the latter is required by MoltenVK's image-storage implementation and is not supplied transitively by the other Apple frameworks. Surface creation consistently obtains its Vulkan instance from the swapchain's initialized context; this also repairs the equivalent stale pre-context-refactor access in the inactive platform branches. The iOS full-client graph now defaults to Vulkan and rejects any other backend; the earlier bootstrap-only return remains unaffected. `VKWindow::createSurface()` has an iOS-only Objective-C++ bridge that obtains Qt's native `CAMetalLayer`; Windows and X11 retain their existing branches. `display-plugins` also skips its redundant direct `target_opengl()` invocation only for iOS with the Vulkan backend; desktop, non-Vulkan, and Android behavior remains unchanged.

The former Qt `GuiPrivate` dependency was caused only by unused `qpa/qplatformnativeinterface.h` includes in `VKWindow.cpp` and `VKWidget.cpp`; all native-interface calls were commented out. Those includes and the unused `QtPlatformHeaders/QXcbWindowFunctions` include are removed, and the X11 header in `VKWindow.cpp` is now restricted to non-Windows, non-iOS builds. The `vk` target therefore links only public Qt Core/Gui APIs. Full iphoneos and iphonesimulator compilation remains the external confirmation that no transitive private-header assumption exists.

## Remaining explicit GL API boundary

Removing `gpu-gl-common/gpu-gl` from backend selection did not by itself make the full application GL-free. After the source gates below, neither Interface nor `display-plugins` retains a direct iOS/Vulkan `gl` link:

- `DisplayPlugin::copyTextureToQuickFramebuffer` now exposes only the backend-neutral `QuickTextureCopyTarget`; Qt OpenGL and GL fence types no longer leak through the public ABI.
- `ResourceImageItem` constructs OpenGL framebuffer objects and waits/deletes GL fences only on non-iOS builds. On iOS it is a non-rendering `QQuickItem` until a native transfer exists.
- The display-plugin library macro still discovers the OpenGL, stereo, and HMD source families, but iOS/Vulkan marks their explicit source list `HEADER_FILE_ONLY` and `SKIP_AUTOMOC`; they are neither compiled nor moc-generated. Registration headers and `DebugHmdDisplayPlugin` construction are also excluded under `Q_OS_IOS`. Interface HMD signal wiring, vision-squeeze dispatch, and the desktop OpenGL sRGB developer toggle are gated by the same boundary, so excluded classes cannot leave unresolved RTTI, metaobject, method, or static-setting references in the device link. `Application_Plugins.cpp` directly includes the backend-neutral `CompositorHelper` that it calls instead of receiving that complete type transitively from the excluded HMD header.
- Interface compilation still directly includes GL helpers in central application, graphics, and menu paths. The safe diagnostic slices are isolated: `main.cpp` includes `GLHelpers` only for macOS/Windows probes; iOS Stats reports zero legacy GL swapchain memory; and `Application_Graphics` skips `gl::ContextInfo` population plus the Chromium AMD/ATI `GL_VENDOR` workaround because MoltenVK has no GL context and iOS uses WebView rather than that desktop WebEngine workaround. `GraphicsEngine` no longer includes the unused `OffscreenGLCanvas`, and its backend header now follows the existing `USE_GL` selection, so a Vulkan build does not parse `GLBackend.h`; its widget, `makeCurrent()`, Vulkan context initialization, render-engine setup, and frame loop are unchanged. The iOS/Vulkan Interface source list also excludes `GLCanvas.cpp/.h`, while desktop/Android OpenGL builds retain them; all translation units include `GLCanvas.h` only when `USE_GL` is selected. The active iOS widget remains `VKCanvas`.
- `RenderEventHandler` no longer includes `OffscreenGLCanvas`: it only owns Qt event/timer state and callbacks, so that transitive GL dependency had no source-level consumer.
- Driver/session telemetry no longer queries `gl::ContextInfo` on iOS. Existing JSON keys remain present with empty/zero GL values for schema stability and gain the real GPU backend version; desktop and Android retain their GL details. The desktop GPU-driver blocklist is skipped on iOS because its Metal driver is delivered with iPadOS and cannot be independently replaced or rolled back.
- `VulkanDisplayPlugin.cpp` retains GL context/helper dependencies beyond the now-gated Quick-copy method.

[`ios/rendering-integration-inventory.json`](../../ios/rendering-integration-inventory.json) records source-anchored migration tasks. The neutral ABI/UI/display-family work, three diagnostic slices, the unused `GraphicsEngine` GL include separation, and the inactive iOS/Vulkan `GLCanvas` exclusion are complete. Non-iOS probing, vendor workarounds, and statistics remain unchanged. Core `Application_Graphics` context creation, the active `GraphicsEngine` widget/context lifecycle, menu, and Vulkan display helper paths remain pending because they participate in context creation or active rendering rather than diagnostics.

Interface now clears its direct `gl` library variable only for iOS/Vulkan. `Application_Graphics` does not include GL helpers, query/set Qt's global GL share context, or issue the legacy clear/swap sequence there. It still calls `VKWidget::createContext()`, `makeCurrent()`, and `GraphicsEngine::initializeGPU()`; the compatibility context inside `VKWidget` belongs to and is linked by the `vk` target. `display-plugins` likewise clears its direct variable: OpenGL/HMD/stereo sources are excluded, Quick-copy/KTX/memory/context-restore branches do not compile, `gl/Config.h` follows the Quick-copy gate, and `CompositorHelper` no longer includes its unused `GLWidget.h`. Desktop and Android retain both original links.

There is currently no reusable Qt Quick Vulkan/QRhi handoff in this source graph. `qml::OffscreenSurface` exposes a `uint32_t` OpenGL texture plus an opaque fence, `SharedObject::initializeRenderControl` requires `QOpenGLContext*`, and its render event handler uses `QOpenGLContextWrapper`. Consequently switching only `QQuickWindow` to Vulkan would break the texture/fence consumer contract. The migration inventory keeps a source-anchored native-RHI task pending rather than claiming support. One legacy context is safely gone already: iOS does not link Qt WebEngine, so `Application_Graphics` no longer creates the Chromium helper's `OffscreenGLCanvas`; the distinct QML shared canvas remains untouched until the complete producer/consumer contract is replaced.

The first compile-time boundary for that migration now exists without claiming a renderer: `OffscreenSurface::SharedGraphicsContext` carries only a backend tag and opaque handle. The QML library currently accepts `OpenGL` and forwards the handle to its unchanged `QOpenGLContext` implementation; unsupported or null leases return `false` without mutating shared state. Desktop therefore keeps the existing GL canvas behavior. iOS supplies `Unsupported/null`, logs a fail-closed diagnostic, and no longer constructs the QML `OffscreenGLCanvas`. A future QRhi/Metal backend must add both a real context implementation and a replacement for the GL texture/fence ABI before changing this result.

`VulkanDisplayPlugin` no longer asks the GL driver for free dedicated memory on iOS because that value cannot describe MoltenVK/Metal allocations; its optional statistic is set to zero until the Vulkan allocator exposes a supported budget query. This removes the iOS `gl/Context.h` dependency. The already fail-closed Quick-copy branch also no longer parses `QOpenGLFramebufferObject`, and two unused context/escrow includes are gone on every platform. KTX1 frame-file capture has no backend-neutral format path: the file header contains GL fields and the repository's only complete `gpu::Element` mapping is `gpu::gl::GLTexelFormat`. Because this is a diagnostic `captureFrame()` path rather than presentation or screenshots, iOS now fails it closed with a one-time warning and does not compile the mapping or its header; other platforms retain capture unchanged.

The last `VulkanDisplayPlugin` reference to `OffscreenGLCanvas` was a context restore after `withOtherThreadContext`. Its thread-local context can only be registered by the QML `RenderEventHandler` on the dedicated QML render thread; iOS reaches this helper only for Vulkan framebuffer screenshot downloads, where Present-thread synchronization is required but restoring an OpenGL context on the caller is not. iOS therefore retains the synchronization callback and excludes only `OffscreenGLCanvas::restoreThreadContext()` plus its header. Non-iOS capture and restore behavior remains unchanged. This does not solve the separate OpenGL QML producer itself; that producer still requires the pending native-RHI migration.

The iOS platform-backend list now contains only `gpu-vk;vk`; its legacy `gpu-gl-common;gpu-gl` bridge list is empty, and both top-level direct GL links are gated away. This is not yet a claim that every transitive target is GL-free: `vk` owns its `VKWidget` compatibility context and `qml` still owns the legacy Offscreen GL implementation, which iOS now rejects through the backend-neutral lease. Those target-owned dependencies are separate from selecting backend implementations through `PLATFORM_GL_BACKEND`.

The inventory now distinguishes these target-owned compatibility dependencies explicitly. `qml -> gl` remains blocked on a native-RHI producer because its render handler creates FBOs/textures and emits `GLsync`; `vk -> gl` remains implemented compatibility infrastructure because `VKWidget` constructs `gl::OffscreenContext` before initializing the Vulkan GPU backend. The separate desktop GL UUID/semaphore capability helpers fail closed on iOS: they perform no GL queries, return no UUIDs, and report external GL interop unsupported. A transitive link is therefore not by itself evidence that Interface regressed to an OpenGL renderer. `OffscreenSurface.cpp` no longer includes `OffscreenGLCanvas.h` merely to forward the new opaque lease; the actual GL producer still includes and owns its concrete canvas.

Those compatibility targets do not use CMake's desktop `FindOpenGL` path on iOS. They retain pinned, statically built glad dispatch with explicit GLES 3.2 generation, link the SDK's deprecated OpenGLES framework, and fail closed if either dependency is unavailable. This is a narrow bridge for the already inventoried QML/VK context ownership, not an OpenGL rendering-backend selection or a substitute for the pending native-RHI migration.

Integrated CI also provisions the Khronos iOS-only MoltenVK archive by an exact version and SHA-256, validates its arm64 static XCFramework slice, and saves the validated distribution as an independent cache checkpoint. Shader host-tool paths are generated and consumed from the staged Conan output, so the target graph does not rely on the desktop recipe's build directory. NVTT and ETC2Comp are target packages rather than host-only tools because the compiled `image` library directly performs their resize and texture-compression operations.

Animated snapshot encoding similarly retains its small static GifCreator target dependency. Legacy QuaZIP is different: the available package is Qt-5-bound, so both link requests are excluded on iOS and the still-exposed archive API fails closed without extracting data. A Qt 6 QuaZIP integration is required before archive import can be enabled on device.

Acceptance is deliberately split into three gates:

1. Source contracts and host validators must pass locally.
2. A real Apple toolchain must configure and link the complete iphoneos Overte graph; host inspection cannot mark this complete.
3. An iPad run must present through the Metal-backed Vulkan swapchain and emit `OVERTE_IOS_ENTITY_GATE render_handoff` for the same world entity UUID previously reported by `entity_tree_nonempty`; bootstrap geometry alone is rejected.

The latter two stay `unverified` in the machine inventory until CI/device evidence is attached.

The integrated iOS graph also runs `RenderingCompatibilityPreflight.cmake` after Interface has materialized its libraries. It fails configuration if any ownership target (`qml`, `vk`, `gl`, `display-plugins`) is missing, if the public context-boundary headers are unavailable, or if `display-plugins` lost `OVERTE_IOS_VULKAN_DISABLE_QUICK_GL_COPY=1`. The resulting interface gate exports only `OVERTE_IOS_RENDERING_COMPATIBILITY_PREFLIGHT=1`; it does not add GL links or claim QRhi support. This makes graph drift fail during configuration while leaving the iphoneos link and device gates honestly external.

The desktop external-texture path depends on GL memory-object imports and `GLsync`; MoltenVK cannot provide equivalent semantics. iOS therefore defines `OVERTE_IOS_VULKAN_DISABLE_EXTERNAL_GL_INTEROP`: external textures return no GPU object with a one-time critical diagnostic, and recycler fence work asserts if it becomes reachable. This is intentionally fail-closed until a native IOSurface/Metal import exists; ordinary entity model/material textures do not use the external-texture contract.

The same boundary now begins at Vulkan device creation. iOS does not request the desktop `VK_KHR_external_memory_fd` / `VK_KHR_external_semaphore_fd` device extensions or their unused instance capability extensions, and it leaves `vkGetMemoryFdKHR` null. A symbolicated simulator crash previously showed that MoltenVK rejected the unsupported device-extension set, while `Context::buildDevice()` ignored that result and immediately called `vkGetDeviceQueue()` with no logical device. Logical-device handles are now initialized to `VK_NULL_HANDLE`, missing extensions return `VK_ERROR_EXTENSION_NOT_PRESENT`, and instance/device creation failures throw before allocator or queue access. Desktop and Android retain their external-FD interoperability requests.

Vulkan shader loading follows the same explicit backend boundary. The runtime loader previously treated every graphics API other than desktop GL 4.5/4.1 as GLES 3.2, so an iOS Vulkan launch loaded only the `310es` resources and then aborted when `VKPipelineCache` requested GLSL 450 reflection and SPIR-V. Vulkan now selects its own GLSL 450-only payload; GLES remains explicitly bound to `310es`, desktop GL keeps its original dialect sets, and an unknown graphics API fails closed instead of silently selecting GLES. A candidate-bound simulator crash and matching dSYM identified the throw in `shader::Source::getDialectVariantSource()` before this boundary was corrected.

Vulkan pipeline cache keys also model draws without vertex inputs explicitly. The backend already accepts a null `Stream::Format` and omits vertex binding and attribute descriptions for those draws, but key generation previously dereferenced that optional format unconditionally. A symbolicated simulator crash placed the fault in `Cache::Pipeline::getKey()` on the Vulkan present thread. Cache keys now encode `absent` separately from an empty-but-present format, preserving both valid pipeline states without a null dereference or a key collision.

Dynamic shaders require a second identity boundary. Their copied `shader::Source` objects deliberately retain `INVALID_SHADER`; keying modules and pipelines only by that numeric ID caused the first procedural vertex module to be reused as the fragment module. MoltenVK then asked SPIRV-Cross for a fragment entry point in vertex SPIR-V and terminated the process. Vulkan module and pipeline caches now use the exact GLSL 450/Mono SPIR-V payload for dynamic sources, while static sources retain their unique compact IDs. Before a module reaches MoltenVK, its size, magic and `main` entry point are checked against the requested vertex or fragment execution model. Runtime text replacements are still not compiled into new Vulkan SPIR-V; this repair restores safe identity and the static fallback payload, but a native runtime compiler or prebuilt procedural variants remain necessary for arbitrary procedural shader visuals.

That preflight also rejects a missing GLSL 450 dialect or Mono variant without dereferencing an absent map entry, and it runs while forming the pipeline key, before render-pass or descriptor/pipeline-layout allocation. The key includes the exact reflection maps used to construct descriptor and vertex-input state, so two dynamic sources with identical SPIR-V but different binding metadata cannot alias. The structural parser walks the complete instruction stream after finding `main`; a malformed trailing instruction therefore remains a rejection rather than being hidden by an early match. The validated shader/reflection identity is cached with the immutable `gpu::Pipeline`, avoiding a full SPIR-V scan and reflection sort on every draw.

Qt owns the iOS `QUIMetalView` and its `CAMetalLayer` on the GUI thread. The Vulkan present thread previously called `VKWindow::resizeFramebuffer()` directly, which let widget geometry and MoltenVK swapchain layer configuration run off-main and produced UIKit diagnostics. iOS keeps `VKWindow` GUI-thread-affined now. The present loop parks before image acquisition while a single queued, lifetime-checked GUI callback performs the device-idle, widget, swapchain, command-buffer, depth, and framebuffer resize transaction; it clears the resize flag only after the transaction commits. A zero-sized surface is deferred, a changed swapchain image count recreates the corresponding command-buffer set, and iOS Vulkan errors throw instead of falling through a release-disabled assertion into partial state. Present submission also retires, waits, destroys, and resets the previous fence/command-buffer pair before either handle is reused; it no longer destroys the newly submitted fence and then stores that invalid handle. Deactivation disables new callbacks before releasing the presentation thread. Desktop retains its existing window-to-present-thread behavior.

The legacy Quick-copy behavior still cannot be implemented on a Metal-only iOS surface, although its public ABI is now neutral. The Vulkan implementation was already an inactive `#if 0` stub on every platform. iOS makes that state explicit with `OVERTE_IOS_VULKAN_DISABLE_QUICK_GL_COPY`, clears the opaque completion token, returns `false`, and emits one critical diagnostic requesting a QRhi/Metal-native bridge. This affects only `ResourceImageItem`-style Qt Quick image copies, not normal entity or material texture upload and rendering.

The gated external-texture class, its GL helper include, GL-typed backend members, and GLsync cleanup are excluded from iOS compilation. Consequently `gpu-vk` no longer links `gl` directly on iOS; non-iOS builds retain the original link. All source-anchored hybrid-backend migration tasks are complete. Full iphoneos and iphonesimulator configuration/linking remains the honest acceptance gate for transitive dependency or platform-plugin issues, followed by the existing entity render-handoff marker on a device; a standalone Metal preview is insufficient.
